# 变更审查（增量）

审查的对象是**改动的增量**，不是整个仓库。把"这个文件写得怎么样"当成结论，
用户拿不到任何可执行信息——他要知道的是「这几行会不会出事」。

## 一、先建立改动清单

1. `code_view(mode=status)` 拿整仓清单：谁改了、谁是新增（`??`）、谁是删除。**不带 path 也能列**，
   所以不要靠猜文件名——猜文件名是这一步唯一的幻觉来源。
2. 再对风险最高的 2-3 个文件 `code_view(mode=diff)` 看具体改动。clean 就是真没有变更，不要想象出变更；
   返回"未追踪文件"时说明它还没 `add`，diff 里看不到内容，要改用 `mode=content` 读。
   单个文件改动过大时，diff 会只展开前几个 hunk 或给一个标好行数的行窗口，
   开头会写明"共几个 hunk、展示了多少"——**没展开的 hunk 就是没看到**，
   不能当成"没改"，要改用 `mode=content` 按 `@@` 行号补读，否则审查结论只覆盖了前 30 行。
   写入时工具返回过改动片段的话，它可以当线索，但**不能当审查依据**：
   片段只带改动处上下各 3 行，证明"改了这几行"，不证明"影响面就这么大"。
3. 涉及多文件时，先按调用链排序：入口 → 服务层 → 数据层。从上游往下游看，
   否则你会先看到下游一堆防御代码，误以为上游没问题。

## 二、按这六个维度过一遍（每个维度只问一句话）

| 维度 | 要问的一句话 |
|---|---|
| 边界 | 空值 / 空集合 / 越界索引进来会怎样？ |
| 超时与重试 | 新加的远程调用有超时吗？重试会不会放大下游压力？ |
| 并发 | 有没有共享状态被并发读写？锁的粒度对吗？ |
| 事务 | 多次写入是否需要同一事务？部分失败会不会留下半成品？ |
| 兼容 | 改了签名/字段/返回结构，旧调用方还活得下去吗？ |
| 可观测 | 出错时日志里有足够信息定位吗（有没有把异常吞掉）？ |

## 三、反向验证（这一步决定结论值不值钱）

对每个你怀疑的点，用 `code_find(mode=regex)` 反查调用方：

- 改了方法签名 → `code_find(mode=refs)` 搜符号，确认所有调用点都改到了；
- 改了返回结构 → `code_find(mode=regex)` 搜字段名，确认消费方没炸；
- 新增了分支 → 搜相关开关/配置，确认默认值符合预期。

**没有反查过的怀疑不要写成问题**，写成「需要确认」并给出确认方法。

## 四、分级与措辞

- `blocker`：会在生产上出错 / 丢数据 / 安全问题。必须给出具体触发路径。
- `warning`：边界情况下可能出问题，或明显偏离项目既有约定。
- `nit`：可读性、命名、注释。**最多三条**，多了就是噪音。

每条都要带 `文件:行号` 和"改成什么"。只指出问题不给改法，等于把活推回给用户。
