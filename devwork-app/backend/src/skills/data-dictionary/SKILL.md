# 数据字典

数据字典最容易变成"看着字段名编解释"。这里的唯一标准是：
**每一句字段说明，要么来自结构（类型/约束/索引），要么来自数据采样，要么标注为推测。**

## 一、结构优先

1. `db_inspect(mode=tables)` 拿全表清单，先按业务域分组，别按字母序排——
   字母序对读者没有意义。
2. `db_inspect(mode=schema, table=...)` 逐表拿列 / 索引 / 外键。这三样决定了字段的**硬事实**：
   - 主键与外键 → 表之间的关系，写进"关联"一栏；
   - 唯一索引 → 这列是业务主键，比注释可靠；
   - 可空 → 这列的取值完整性假设。
3. `db_inspect(mode=counts)` 拿行数画像。行数是选型与排查的第一信息：
   一张 30 行的配置表和一张 3000 万行的流水表，说明写法完全不同。

## 二、用数据确认字段语义（不要猜）

对有歧义的字段，跑一条**极小的**采样查询：

```sql
SELECT status, COUNT(*) AS n FROM "order" GROUP BY status LIMIT 20
```

- 枚举型字段：`GROUP BY` 看出真实取值域，比读注释准——注释往往落后于代码。
- 状态类字段：顺带看清是否存在历史遗留值（如 `CANCELLED_OLD`）。
- 时间字段：抽一条看是秒还是毫秒、是 UTC 还是本地时间。**这类猜测错一次就是数据事故。**

查询一律只读、带 LIMIT，不要为了"看全貌"扫全表。

## 三、标注来源（三档，不能混用）

| 档位 | 标记 | 含义 |
|---|---|---|
| 结构事实 | 〔结构〕 | 类型、约束、索引、外键，直接来自 `db_inspect(mode=schema)` |
| 数据事实 | 〔采样〕 | 来自 GROUP BY / 抽样，注明采样时间与行数 |
| 推测 | 〔推测〕 | 只有字段名可依，必须写明依据与不确定点 |

`kb_search` 能查到团队已有的口径文档时，优先引用它并把来源链写全
（文档名 + 位置），这比你的推测有价值得多。

## 四、交付形态

每张表一节：表用途（一句）→ 行数量级 → 字段表（字段 / 类型 / 可空 / 说明 / 来源档位）
→ 关联关系 → 已知问题（缺索引、字段废弃、口径不一致）。

表很多时先给索引页 + 按域拆分成多节，不要糊成一张巨表——那张表没人会读。
