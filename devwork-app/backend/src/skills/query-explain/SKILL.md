# 执行计划判读

> 与内置技能的分工：`slow-query` 负责"从慢日志里找出是哪条 SQL"，`perf-triage` 负责端到端分诊；
> 本技能只管一件事——**拿到一条具体语句后，怎么读懂它的计划并给出可验证的结论**。

"这条 SQL 慢"是一个结论，不是一个观察。观察只有三样：**计划、规模、实测耗时**。
三者对不上时，说明真正的瓶颈不在 SQL 里。

## 一、三个判据各自的含义

| 判据 | 怎么拿 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| 执行计划 | `db_inspect(mode=explain, sql=...)` | 打算怎么取数（走索引 / 全表扫 / 临时 B 树） | **不回答"慢不慢"** |
| 数据规模 | `db_inspect(mode=counts)` | 表有多大 | 不回答分布是否倾斜 |
| 实测耗时 | `db_query` 看返回的 `durationMs` | 这条查询在这个库上真实花多久 | 不回答为什么 |

最常见的错误是拿计划当耗时：看到 `SCAN` 就说"慢"，但表只有 200 行时全表扫比走索引还快。

## 二、按这个顺序查

1. **先看规模**：`db_inspect(mode=counts)`。行数在千级以下，索引基本不是瓶颈——
   这时候该怀疑的是查询次数（N+1）而不是单次查询。
2. **再看计划**：`db_inspect(mode=explain, sql=...)`。重点不是有没有 `SCAN`，而是：
   - `SCAN table` → 全表扫。表大才有问题；
   - `SEARCH table USING INDEX` → 走索引，通常没问题；
   - `USE TEMP B-TREE FOR ORDER BY` → 排序没吃到索引顺序。**这是最常见的隐藏成本**，
     哪怕其它部分都走索引，排序也能把整个查询拖慢；
   - 同一个 `SUBQUERY` 出现多次 → 它被执行了多次，不是一次。
3. **最后实测**：`db_query` 跑同一条语句，看 `durationMs`。
   - 计划好但实测慢 → 瓶颈不在 SQL（网络 / 锁等待 / 应用层循环）；
   - 计划差但实测快 → 数据量小，别为了"优化"去加索引（写放大是真实成本）。

## 三、结论要怎么写

写成三段，每段都有出处：

```
观察：ORDER BY created_at 触发了 TEMP B-TREE（explain 第三行）
规模：orders 表 120 万行（counts 实测）
结论：排序没吃到索引，120 万行下这在每次请求里都要重排一遍 — 加 (created_at) 索引可消除
```

不要写的两种：

- "可能缺少索引"——缺哪个？哪条语句的哪一步？没说就是猜；
- "建议加索引优化性能"——没有数据支撑的建议，改完也不知道有没有用。

## 四、写操作的边界

索引变更（`CREATE INDEX`）是 DDL，不属于 `db_query`（只读）也不属于 `db_query_write`（DML）。

**正确的做法是产出建议，让用户执行**：给出完整的 DDL、说明预期收益与代价（写放大、磁盘、锁时间），
不要试图绕过工具限制去"顺手建个索引"。

## 五、排查常见死路

- **反复改 SQL 试**：每改一次都要重新 explain + 实测，否则你只是把不确定性搬了个地方；
- **看到慢就拆表**：先确认是单次慢还是次数多。分页与批量取数能解决的问题，拆表解决不了；
- **忽略数据倾斜**：平均值 5ms 不代表每个请求都 5ms。用 `db_query` 看分布（`ORDER BY` 耗时字段）
  往往比看平均值有用。
