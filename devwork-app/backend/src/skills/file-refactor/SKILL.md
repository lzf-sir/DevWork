# 文件重组

文件组织操作的风险不在"改了什么"，而在**"删了以后还能不能回来"**。

## 一、先确认三件事，再动手

1. **这个文件真的没人引用吗**——删之前用 `code_find(mode=regex)` 搜文件名（不带扩展名）与
   类名/函数名。搜不到不等于没人用：动态加载、配置里写死的路径、外部调用都搜不到。
2. **它进过版本库吗**——`git_history(mode=log, path=...)` 能查到提交记录，说明历史里有备份，
   删了还能从 git 找回；查不到说明是新增未提交的文件，**删了就真没了**（回收站是最后一道保险）。
3. **目标路径存在吗**——`fs_manage` 的 move/copy 目标必须不存在。不要指望它覆盖。

## 二、顺序：先复制后删除

大范围重组（比如把一个文件拆成三个模块）不要一步到位：

```
① fs_manage(mode=mkdir)   建新目录
② fs_manage(mode=copy)    先把文件复制过去（源还在）
③ code_edit(mode=replace) 在新位置改内容
④ 确认新结构能跑（让用户验证，或看构建结果）
⑤ fs_manage(mode=delete)  最后才删旧的
```

反过来的顺序（先删后建）在出问题时**没有退路**：审批卡一次只能批准一步，中间失败就是半成品。

## 三、delete 的真实语义

`fs_manage(mode=delete)` **不是真删**：文件被移到运行时数据目录的回收站，审批卡上会给出回滚引用。

- 回滚按钮能把文件移回原路径（原路径被占用时会拒绝，不会覆盖）；
- 但回收站不是永久档案：它随运行时数据目录清理。**要留的东西请提交进 git**；
- 删除目录会整个移走。审批前看清楚路径末尾是文件还是目录——审批卡上的 `args` 是最后的确认点。

## 四、什么时候不要用 fs_manage

- **要改内容**：用 `code_edit`。move 之后再 rewrite 是两次审批，能一次说清就别拆两步；
- **工作区文件**：`fs_manage` 只作用于代码库。工作区文件的写入走 `fs_write_file`；
- **跨仓库搬运**：两条路径都必须落在**同一个**仓库内。跨仓库要分两步，且第二步要重新审批。

## 五、报告纪律

组织操作做完要能回答"现在是什么状态"：

- 移动：`旧路径 → 新路径`，并说明引用是否需要同步更新（改了没改，都要说清）；
- 删除：写清"已移入回收站，可回滚"，不要写"已删除"——那会让人以为找不回来了；
- 失败：precheck 失败通常意味着**你对现状的判断是错的**（文件不存在 / 目标已存在 / 路径越界）。
  如实报告失败原因，不要换一个路径重试到"看起来成功"。
