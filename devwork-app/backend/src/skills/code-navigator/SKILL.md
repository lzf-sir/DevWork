# 代码定位导航

目标不是"读了很多文件"，而是**用最少的调用把范围收敛到几行**。顺序错了会一直读不完。

## 一、先决定用哪种判据（mode）

| 你手上的线索 | 用哪个 | 为什么 |
|---|---|---|
| 只知道大概意思（"下单超时是怎么判定的"） | `code_find(mode=index)`（FTS 索引） | 先摸出候选文件，快但可能滞后于工作区 |
| 知道具体标识符（`setConnectTimeout`） | `code_find(mode=regex)` | 磁盘真实匹配，证据最强，带行号 |
| 知道命名规律（"所有 mapper"） | `code_find(mode=glob)`（`**/*mapper*.ts`） | 不读内容，最省额度 |
| 已知文件、要理解结构 | `code_view(mode=outline)` 看大纲 | 带起止行与所属类，比从头读全文省一个数量级 |
| 要判断"还有谁在用它" | `code_find(mode=refs)` | 词法级：注释/字符串里的同名文本已排除；同名不同符号不合并，而是分组列出 |

`code_find(mode=index)` 拿到候选后，**必须**用 `code_find(mode=regex)` 或 `code_view(mode=content)` 复核一遍再引用行号——
索引可能落后于工作区，拿索引行号当事实是这套工具最容易出错的地方。

## 二、收敛顺序（照这个做）

1. **定范围**：`code_find(mode=regex)` 的正则先窄后宽。先搜最具区分度的标识符，命中 0 条再加宽；
   一次就搜 `error` / `get` 这种泛词，会拿到几百条等于没搜。
2. **看结构**：拿到文件先 `code_view(mode=outline)`，按输出里的 `L起-止` 精确读那个方法，而不是整文件读。
   大纲里出现 `L12` 而没有区间，说明这个方法没解析出闭合大括号——按起始行往下读，别假设它只有一行。
3. **读上下文**：`code_view(mode=content)` 带 `offset`/`limit`，从命中行往前 20 行、往后 40 行读。
   返回里写着"还有 N 行未读"时，**不许**对这个文件的整体行为下结论。
4. **验闭环**：找到定义后，用 `code_find(mode=refs)` 反查调用点。refs 会分成
   "定义 / 引用"两栏，并单独告诉你"注释与字符串里还有 N 处已排除"。
   只看到定义不算定位完成——同一个方法可能有九处在用，问题出在第十处。
5. **遇到「同名候选分组」先看它再下结论**：分组表只按**书写形式**分，不推断类型。
   - `定义落在 N 个容器`：说明这名字本来就不止一个符号，先把你要的那个挑出来再说条数；
   - `定义 1 处`：引用大概率同源（依赖里的同名方法不在扫描范围）；
   - `引用按接收者：order 3、user 1`：真正在用的是哪个变量，一看就知道。
   但**不要把 refs 的条数当"调用次数"**：同一个接收者也可能来自不同类，条数只代表"代码里出现几处"。
6. **定义散在多个文件时，看「跨文件收敛」表**：它按每个文件**真实的 import 语句**判断
   这个文件里的同名引用归到哪一处定义。四种行要分清：
   - `导入 ../defs/user → defs/user.ts`：这个文件与那处定义同源。括号里是证据强度——
     `import 名单里就有这个符号` 是强证据，`只导入了模块` 只说明文件同源，调用本身没被证明；
   - `导入了 N 个定义文件，无法拆分`：这个文件里两处同名调用**可能不是同一个**，
     必须按接收者逐处看（`u.save()` / `o.save()`），别合并成"2 处引用"；
   - `没有 import 证据，无法归属`：同包、全局注入、来自依赖都可能，不要猜；
   - `引用与定义同文件`：这条最干净，按文件内的大纲区间读就行。
   收敛只覆盖 ts/java/python/go/rust 的导入语法；别的方言一律落在"无法归属"，这是限制，不是结论。
   改签名时把这张表抄进定位单——它就是"改后重放"要对照的那份名单。

## 三、必须停下来的信号

- `code_find(mode=regex)` 命中 0 条，但你已经"确定"代码在这里：说明假设错了，回头改假设，不要换同义词硬凑。
- 连续两次 `code_view(mode=content)` 都提示"还有 N 行未读"：说明该换方法了（先 outline 定方法，或缩小范围），
  继续翻页只是把上下文烧光。
- 你觉得"应该是这样实现的"：这句话是幻觉的前兆。要么有命中结果，要么就写"未确认"。

## 四、输出：一张能直接交给下一步的定位单

每条结论带 `文件:行号`，并写清证据来自哪个 mode（regex 命中 / content 读到的原文 / refs 的定义处）。
定位之后**如果还要改代码**，先把它整理成定位单——下一步（`write-safety`）的"改后验证"
就是拿这张单子逐条重放的，不是重新猜一遍：

```
定位单
- 定义：src/.../OrderService.java:L120-L140（OrderService.createOrder）
- 待改处：L128（`repo.save(entity)` 这行）
- 调用点：refs 接收者分组 order 3 / service 1（共 4 处引用，1 处定义）
- 未确认：L118 的 `repo` 字段类型没读到（在此文件外声明），改参数前要确认
```

四栏缺一栏，改完就会漏：没有"待改处"会改错行，没有"调用点"会漏改调用方，
没有"未确认"会把猜测当成事实带进下一步。

任务跨轮次时，把这张单子 `memo(mode=write)` 记一条。上下文一压缩，定位单是最先消失的东西，
而它正是改后验证的基线——丢了就只能重新搜一遍，然后把"搜到的"当成"当年查到的"。

定位失败就如实说"在 X 范围内没找到"，并给出你搜过的模式——让用户能判断是搜错了还是真没有。
